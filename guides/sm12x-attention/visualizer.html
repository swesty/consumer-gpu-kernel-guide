Why these two GPUs are their own target

A fast attention kernel has two halves: staging (getting K and V tiles from GPU memory into the small on-chip scratchpad called shared memory) and math (the tensor-core matrix multiply). Hopper and data-center Blackwell each have a special math instruction that SM120 and SM121 do not have, and the two workstation parts have less than half the shared memory. A kernel written for H100 or B200 therefore cannot simply be recompiled.

Staging: TMA bulk copy.
Math: wgmma — a whole warpgroup (4 warps) issues one asynchronous multiply; operands read straight from shared memory.

Workstation Blackwell · SM120 / SM121

Staging: TMA bulk copy is available, as is the older cp.async.
Math: mma.sync — each warp multiplies a 16×8 tile and keeps the result in its own registers. No wgmma, no tcgen05, no TMEM.

99 KB / block

What SGLang has that vLLM does not, on these GPUs

  • A working FA4 on SM12x. SGLang ships its own major-12 FA4 kernels behind --attention-backend fa4. vLLM never selects FA4 on major 12 and its bundled upstream path cannot read a paged cache.
  • FMHAv2 prefill. SGLang's trtllm_mha uses FlashInfer's FMHAv2 for prefill on SM120; vLLM's FlashInfer backend keeps SM12x prefill on fa2.
  • Per-phase backend flags. --prefill-attention-backend and --decode-attention-backend let one server mix, for example, fa4 prefill with XQA decode — a ready-made A/B harness.
  • The reverse: vLLM has b12x paged attention as a first-class backend; SGLang main uses b12x only for GEMM.
Your fleet, per your own vault note (last checked 2026-10-10, re-probe before relying on it): the standard Spark image carried FlashInfer 0.6.16.post3 and the DeepSeek image 0.7.0. The b12x attention backend needs flashinfer-python ≥ 0.7.2, so it is absent from both until the image is rebuilt.

Each item below is something a fast kernel on SM120 / SM121 needs, that exists in some form, and that is unfinished, unmerged or switched off. Every card defines the idea from scratch, then lists where it stands.

Paged KV cache FA4 SM120: not merged b12x, FA2, FlashInfer: yes

What it is. While generating, a model keeps the keys and values (K and V) of every earlier token so it never recomputes them — the KV cache. A server handling many requests cannot give each one a single contiguous slab, because requests grow and finish at different times. So it cuts memory into fixed-size pages (blocks of, say, 16–128 tokens) and gives each request a block table: a list saying "my tokens 0–63 are in page 7, tokens 64–127 are in page 2…". It is virtual memory for attention.

Why it is hard for a kernel. A kernel written for one contiguous tensor computes an address with a multiply. A paged kernel must look up the block table for every tile it loads, and a tile may straddle two pages that are nowhere near each other. That lookup sits in the hottest loop, and it complicates TMA, which wants one regular box of memory per copy.

  • Upstream FA4 SM120: "Paged KV not supported on SM 12.0" (assertion) issue #2307. BF16 paged PR #2348 is open, needs a rebase, and is labelled non-TMA; #3060 (extend paged KV from SM90 to SM80/SM120) is open.
  • vLLM and SGLang store only paged caches, so a kernel without this cannot be served — which is why upstream FA4 on SM120 is unusable in vLLM even though its dense kernel works.

Split-KV decode FA4 SM120: forced to 1 split FlashInfer runtime split-KV: data-center only

What it is. Attention work is normally divided along the query axis: each thread block takes a slab of query rows. During prefill there are thousands of query rows, so every part of the GPU is busy. During decode there is one new token — one query row — attending to the whole cache. Divide one row among blocks and you get one block: a single streaming multiprocessor walks the entire cache while the others idle.

Split-KV cuts the other axis. The long K/V sequence is divided into chunks, each chunk goes to a different block, and each block returns a partial output plus the log-sum-exp of its attention scores. A small final step uses those log-sum-exps to weight and merge the partials into exactly the answer one block would have produced.

Why it is hard. The number of splits is a tuning decision that depends on batch size, context length and the number of multiprocessors (48 on the Spark, about 188 on the RTX PRO 6000). Too few leaves the GPU idle; too many pays launch and merge overhead for nothing — and with a full batch the query axis already fills the GPU, so splitting only costs.

  • Upstream FA4 SM120: num_splits is asserted to 1 issue #2307; BF16 SplitKV PR #2336 open and stalled since 2026-08-14 issue #2996; "per-batch SplitKV building blocks" PR #3108 open.
  • FlashInfer v0.7.4 added "automatic runtime split-KV" to its Prims-TS attention; that paragraph names B200 / B300 only rel.
  • FA2, the vLLM default on SM12x, has had split-KV decode since 2023 — one concrete reason an "older" kernel can win decode.

FP8 and NVFP4 KV caches uneven across kernels

What it is. K and V are normally stored as 16-bit numbers (BF16). Storing them as 8-bit floats (FP8, format e4m3) halves the cache; NVFP4 stores 4-bit values plus one shared 8-bit scale per 16 values, about 4.5 bits each. A smaller cache means longer contexts in the same memory and fewer bytes to read on every decode step.

Why it is hard. There are two ways to use a compressed cache. The easy way converts each tile back to 16-bit after loading it — memory is saved but the math is unchanged. The fast way feeds 8-bit operands directly to the tensor cores, which requires the query in FP8 as well, a per-tile or per-token scale carried through the softmax, and a kernel compiled for that instruction. Every combination (FP8 × paged, FP8 × split-KV, FP8 × sinks) is separate code.

  • FA2 (vLLM default on SM12x): no FP8 KV at all docs.
  • FlashInfer on SM12x: FP8 / NVFP4 KV work, but the query stays 16-bit — "Architectures with only fa2 (e.g. SM89, SM120) cannot consume FP8 queries" src: vLLM flashinfer.py.
  • FMHAv2 prefill on SM120: no fp8_e4m3 KV src: SGLang.
  • Upstream FA4 SM120: FP8 forward PRs #2980 and #3132 open. #2980's paged path "is FP8-only by contract" and rejects BF16 paged calls, so neither dtype has a complete merged paged path issue #2996.
  • SGLang SM12x FA4: native FP8 KV is PR #45871, open issue.
  • b12x: FP8 e4m3 KV accepted in vLLM source; the docs table still lists only auto — an unresolved docs/source disagreement.

TMA staging with warp-level math exists; correctness bug open in the GEMM cousin

What it is. TMA (tensor memory accelerator) is a hardware copy engine: one thread describes a box of a tensor and the engine moves it from GPU memory into shared memory in the background, signalling a barrier when done. The alternative, cp.async, has every thread issue its own small loads. TMA frees threads and registers for math and makes a producer / consumer pipeline natural: one warp keeps a ring of shared-memory slots full, the others drain it with mma.sync.

Why it is hard here. Hopper kernels pair TMA with wgmma, which reads operands from shared memory directly. On SM12x the consumer warps must first pull each tile from shared memory into registers (ldmatrix) and then multiply. Two kinds of memory access now touch the same slot — the consumers' ordinary reads and the engine's asynchronous writes — and the hardware does not order them against each other unless the kernel issues an explicit fence. With only 99 KB there are few slots, so they are recycled aggressively.

  • flashinfer#7675, open since 2026-10-28: the b12x MXFP8 GEMM on SM120 returns wrong tiles under CUDA-graph replay with concurrent work, because a slot's TMA refill is not ordered after the consumers' reads. Reporter's one-line fix: fence_proxy("async.shared"); 1,537 bad replays → 0 in the reporter's sweep. Fix PR #7676 referenced, state not verified. issue
  • That report is about GEMM, not attention. It is listed because any TMA + mma.sync attention pipeline has the same hazard, and because eager-mode tests passed — only graph replay under load exposed it.
  • Upstream FA4's SM120 paged PR is explicitly "non-TMA" issue #2996. b12x paged decode stages K/V with TMA, using the page id as a tensor coordinate; its prefill kernel mostly uses cp.async. Its paged-attention files contain no proxy fence, so whether the same hazard applies there is open src.

b12x is opt-in, with a narrow contract works when selected

What it is. "Automatic selection" in vLLM walks a fixed priority list and takes the first backend that validates — the first that can run the configuration, not the fastest. b12x is not on the list for any hardware, so on SM12x a user who passes no flag gets FA2 and never learns b12x exists.

  • Not in _get_backend_priorities for major 12 src: vllm/platforms/cuda.py. Published numbers exist only for related kernels: an upstream pull request reports new BF16 SM12x kernels at about 1.1–1.2× over FA2 on an RTX PRO 6000, and slower than FA2 on many decode shapes issue.
  • Missing pieces that would keep it from being a default: head dimension 64 (excluded pending flashinfer#6977), FP16 models, non-causal attention, multimodal prefixes, and decode context parallelism — splitting one request's KV cache across several GPUs, which a 2 × RTX PRO 6000 or 2 × Spark setup would want src: b12x.py.
  • Prefill runs eagerly rather than inside a CUDA graph (a pre-recorded launch sequence that removes per-step Python overhead) src.
  • A separate, deliberate policy applies to b12x's FP4 GEMM: FlashInfer excludes SM121 from auto-selection there, commenting that cutlass/cudnn are faster on GB10 in most cases your vault note, 2026-09-10 source inspection. That is a GEMM policy, not an attention one; the vLLM b12x attention backend accepts both (12, 0) and (12, 1).

Build the harness before touching a kernel

Two failure modes dominate this area: benchmarking a kernel that was not the one that ran, and shipping a fast kernel that is subtly wrong. The harness exists to rule out both.

Record
GPU and compute capability; vLLM / SGLang / FlashInfer / flash-attn commit; the backend and kernel named in the startup log; head dimension; query-heads : KV-heads ratio; page size; KV dtype; query length, KV length, batch.
Correctness oracle
An FP32 reference (torch.nn.functional.scaled_dot_product_attention on a gathered, de-paged copy). Compare per-row maximum absolute and relative error with a tolerance chosen per dtype. Include masks, sinks, sliding window, page-boundary lengths (page size ± 1) and a context long enough to wrap every pipeline slot.
Stress gate
Re-run every case under CUDA-graph replay with unrelated work on a second stream. flashinfer#7675 passed eager tests and failed only this way.
Two levels
A kernel microbenchmark (one call, fixed shape) and a served benchmark (time to first token, inter-token latency). A combined tokens-per-second number hides a prefill win paired with a decode loss.
Done when
One command produces a table row for (machine, engine, backend, phase, shape) with a correctness verdict attached.

Decide what actually limits each machine

The same roofline reasoning used for the course's GEMM kernels applies: compare achieved bytes per second against the memory ceiling and achieved multiply throughput against the tensor-core ceiling.

Hypothesis A
On the Spark, decode at long context is bandwidth-bound for every kernel, so kernels differ little and KV precision dominates. Falsified if two BF16 kernels differ by more than about 20% at batch 1 with a 32k context.
Hypothesis B
On the RTX PRO 6000, batch-1 decode is occupancy-bound: most of its ≈188 multiprocessors idle unless the KV axis is split. Falsified if achieved bandwidth is already near the ceiling without split-KV.
Tools
Nsight Compute per kernel (memory throughput, tensor-core utilisation, shared-memory use, registers per thread), with the same report layout already used for kernels 8–14.
Decision
If A holds, do phase 5 first on the Spark. If B holds, do phase 3 first on the PRO 6000.
3

Split-KV for the SM12x path

Question
For a given (batch, context, multiprocessor count), how many splits minimise decode latency, and does one heuristic serve both 48 and ≈188 multiprocessors?
Start from
Split-KV already exists in FA2, FlashInfer fa2, XQA, b12x decode and SGLang's SM12x FA4; only upstream FA4 lacks it (PRs #2336, #3108, #3109). The open work is the heuristic: each kernel sizes splits differently, and none was calibrated on a 48-SM Spark.
Experiment
Sweep num_splits ∈ {1, 2, 4, …} against batch and context on both machines; fit the crossover; compare the fitted rule with the SM100-derived heuristic.
Contribution
Either a revived, rebased #2336 with SM12x numbers, or a documented finding that the existing heuristic mis-sizes splits on 48 multiprocessors.
Risk
With FP8 the reduce step must merge partials that carry scales; define that contract before optimising.
4

Staging: when does TMA beat cp.async with warp-level math?

Question
At 99 KB, with mma.sync consumers, for which tile geometries and head dimensions does a TMA producer/consumer pipeline beat a tuned cp.async pipeline?
Already exists for decode
Page-aligned tiles. b12x decode and one SGLang specialization make the KV tile divide the page size, so each tile is one TMA copy with one block-table lookup. The open case is prefill: b12x and SGLang both stage paged prefill with cp.async and a per-row or per-thread page lookup.
Compare
Four variants at identical semantics and precision: FA2 as shipped; cp.async + mma.sync tuned for SM12x; TMA + mma.sync tuned independently; b12x. Sweep stages (2 / 3 / 4) and tile sizes within 99 KB.
Gate
The phase-0 graph-replay stress test, with and without the proxy fence, before any timing is trusted.
Honest prior
TMA helps most where staging, not math, is the bottleneck — long prefill with large head dimensions. Phase 2 may show decode on the Spark gains nothing from it.

Compressed KV with native low-precision math

Question
Can the SM12x path multiply FP8 operands directly instead of widening to 16-bit after load, and how much accuracy does each cache format cost?
Check first
Your vault notes state SM12x tensor cores accept FP8 e4m3 and block-scaled FP4 natively. Confirm against the PTX documentation and a ten-line test kernel before designing around it.
Experiment
BF16 KV vs FP8 KV (widen after load) vs FP8 KV (native multiply) vs NVFP4 KV, on decode latency and on output error against the FP32 oracle and a task-level metric.
Start from
flash-attention #2980 / #3132 (FP8 forward on SM12x), SGLang #45871 (native FP8 KV for its SM120 FA4 kernels), FlashInfer's NVFP4 KV paths for sparse MLA.
Report
Speed and accuracy as separate columns. A cache-precision change is not a free exact-attention speed-up.

b12x into vLLM's automatic list for the shapes where it wins; head dimension 64 for b12x (flashinfer#6977); a BF16 paged path for upstream FA4 SM120; a Spark-specific split heuristic.
What reviewers lack
Hardware. Before/after numbers from a real GB10 and a real RTX PRO 6000, with the correctness harness attached, are the scarce input.
Smallest experiment that would change this plan. On each machine, serve one BF16 head-dimension-128 model twice — once with no flag and once with --attention-backend b12x — and measure batch-1 inter-token latency at a 32k context. If the two differ by less than measurement noise on the Spark but clearly on the RTX PRO 6000, hypotheses A and B both stand and the phase order above is right. If b12x wins clearly on the Spark too, decode there is not purely bandwidth-bound and phase 3 moves ahead of phase 5.

Known disagreements and gaps

  • vLLM's docs table lists FlashInfer compute capabilities as 8.x–9.x, 9.0 and 10.x, but the source accepts up to 12.1 and contains explicit SM12x branches. The source was taken as authoritative.
  • vLLM's docs list b12x KV dtypes as auto only; b12x.py also accepts bfloat16, fp8 and fp8_e4m3.
  • vLLM's FA4 row says "≥ 10.0", yet FA4 is chosen automatically only for major 10, and vLLM's in-tree gate reports FA4 as unsupported outside 9.x–11.x. Forcing flash_attn_version=4 on major 12 is expected to fail at startup (read from source, not run).
  • Two older vault notes say "FA4 is tcgen05-only → SM100 only". Upstream now has a separate SM120 mma.sync path, so that sentence is out of date; the practical conclusion (not servable on the Spark through vLLM) still holds for a different reason.
  • Memory bandwidth is from NVIDIA's pages (1,792 GB/s and 273 GB/s). The multiprocessor counts (188 and 48) are derived from core counts, not read from a device.
