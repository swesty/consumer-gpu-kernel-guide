TensorFold vs vLLM on DGX Spark

Where TensorFold's decode lead over vLLM actually comes from, what is worth bringing into vLLM, and how far one of those ideas got on the spark-3 + spark-4 pair.

2026-11-18 TensorFold 8cbef97 vLLM main as of 2026-11-18 Fleet lane: vLLM 0.1.dev21553+gab86b7073

Summary

Does TensorFold do something vLLM can't?

Mostly no. On GLM-5.3-Flash, most of its 1.45–2.26× decode lead comes from serving fewer weight bytes per token. It requantizes the checkpoint's BF16 non-expert weights to 4-bit at load. Per byte, vLLM's Marlin kernels are faster than TensorFold's.

What is worth porting?

Two things: the b12x RoCE one-shot all-reduce for TP across Sparks, and "log and fold" rollback of linear-attention state under speculative decoding. The RoCE all-reduce already exists in the vLLM fork the fleet runs. It had been silently failing at startup because of a GID-index bug. Once fixed, it measured +7–11% decode at one stream in a fresh-start A/B/A, and +2–6% at four, within noise.

TensorFold does have three real structural differences:

  • bit-exact guarantees (batched equals solo, drafted equals serial);
  • recurrent-state snapshots every 64 tokens for hybrid attention models;
  • per-stream draft depth chosen by a cost model.

vLLM stays ahead on cold prefill, maturity and API breadth.

Where TensorFold's speed comes from

The cleanest evidence is jayleaton's comparison against a vLLM kit (Reederey87's fork of MiaAI-Lab's kit). It uses the same abliterated EXL3 GLM-5.3-Flash weights, the same two Sparks at TP=2 and the same benchmark client. Both stacks load the same DFlash2 drafter. The ladder walks TensorFold from upstream to its tuned build one change at a time. Measured

How the conclusion follows.

  • Observation: with BF16 non-expert weights, TensorFold is only 1.26× faster on chat and is 0.90× (slower) on structured output. The 4-bit requantization (q4mse, patch 0001) is the largest single step.
  • Mechanism: decode on a GB10 is limited by memory bandwidth (273 GB/s), so reading fewer bytes per token yields proportionally more tokens per second.
  • Conclusion: most of the gap is a quantization choice, not a kernel advantage.

Where vLLM stays ahead:

  • Cold prefill: TensorFold reaches 0.87–0.89× on RigMark, but with different weights. On the same weights TensorFold is 1.11–1.15× faster.
  • 4-stream time to first token: vLLM 0.81 s vs TensorFold 0.84 s.
  • Kernel efficiency per byte, API breadth (logprobs, n>1) and maturity.

The 4-bit non-expert path has a quality cost: it changes 13 of 200 MMLU answers. Measured

EXL3 decode, compared with the vLLM kit

vLLM main has no EXL3 support; the vLLM kit adds it through exllamav3. On the routed experts, TensorFold's decode differs from the kit's default single persistent exl3_moe kernel in five ways. Source

  • An expert-major routing plan built on the GPU. The kit uses about a dozen torch ops per layer instead.
  • Trellis words decoded straight into tensor-core registers, without staging through shared memory.
  • A fixed-order split-K merge with no float atomics. The kit combines expert outputs with fp32 atomicAdd.
  • One input rotation per token when every expert shares the same rotation.
  • 16-byte non-coherent loads issued a step ahead (+3.3%), and L2 prefetch during collectives (+2.4%).

Both stacks' own docs, however, put routed-expert streaming at about 210–240 GB/s. So the EXL3 kernel itself is unlikely to explain much of the end-to-end gap. Inference

What to bring into vLLM

  1. 1RoCE one-shot all-reduce for TP across Sparks FlashInfer main ships it (flashinfer/experimental/b12x/comm/roce: all-reduce ≤ 2 MiB, all-gather, world 2–16, graph capture). Upstream vLLM has no communicator for it. The local-inference-lab fork does: b12x_roce_all_reduce.py behind VLLM_ENABLE_ROCE_ALLREDUCE=1. Value: +6–11% at 1 stream in TensorFold; on this fleet's vLLM lane, +7–11% at 1 stream and +2–6% (within noise) at 4 (A/B/A below). Cost: about 1.3 GiB more at startup. Risk: by design it stops rather than falling back to NCCL; a stalled RDMA wait fails the step.
  2. 2"Log and fold" rollback for GDN and KDA layers vLLM keeps a full recurrent state per draft position (num_spec+1 slots). TensorFold logs small per-token records and folds only the accepted rows (qwen35_keep.cu, common/kda.cuh replay). vLLM has this only for Kimi-K3 (RecoverSSM), and its CuTe commit is gated to SM10x. Value: about 1–4% decode at 1–8 streams, plus about 160 MiB less state per request (arithmetic). Risk: invasive changes to cache-slot plumbing.
  3. 3L2 prefetch on a side stream during collectives A small cp.async.bulk.prefetch.L2 op over a load-time table of the next layer's dense and shared-expert weights. Value: +0.8–1.9% at TP=2, +3–4% at TP=3 on GLM. Risk: measured as a loss on Qwen-27B and Nemotron, so it must be gated per model.
  4. 4Deterministic grouped EXL3 MoE decode (only if serving EXL3) Port from TensorFold v0.6.0 cuda/exl3/experts_grouped.cuh, which already has PyTorch bindings. Before porting, try the kit's own GLM53_EXL3_MOE_FAST=1, which claims +8–15%. Value: uncertain, since the stock kernel is near the bandwidth ceiling. Risk: fp32 intermediates shift draft acceptance.

The biggest lever is not a kernel. It is 4-bit non-expert weights, a quantization recipe that vLLM's int4 Marlin path already serves faster per byte than TensorFold's kernel. Weigh it against the MMLU drift above.

Fleet case study: RoCE on the spark-3 + spark-4 lane

The lane serves GLM-5.3-Flash NVFP4 (eugr PR #421 recipe, TP=2 + DCP=2, MTP k=3) on image glm53-b12x:ab86b70. It is published through LiteLLM as workhorse-large. Its recipe already set VLLM_ENABLE_ROCE_ALLREDUCE=1.

Finding: RoCE never came up

The startup log of the container that ran from 2026-11-04 to 2026-11-18 showed the attempt failing on both ranks. vLLM then fell back to PyNCCL for the TP, DCP and EP groups. Measured

RoCEnante initialization failed: RoCE all-reduce setup failed:
  rank 0: RoCE proxy setup failed: ibv_query_gid: Invalid argument
  rank 1: RoCE proxy setup failed: ibv_query_gid: Invalid argument
Using ['PYNCCL'] all-reduce backends ... for group 'tp:0'

Root cause, in three steps:

  1. The cluster launcher exports NCCL_IB_GID_INDEX=-1, which tells NCCL to choose the GID itself. Measured
  2. b12x's default_gid_index() falls back to that variable when B12X_ROCE_GID_INDEX is unset, and passes -1 literally to ibv_query_gid, which returns EINVAL. Source
  3. FlashInfer main has the identical function, so upgrading FlashInfer does not fix it. Source

A fixed index cannot fix it either, because the right index differs per node. Each GID table depends on the order the node's addresses appeared. spark-3's fabric profile adds a second link-local address that pushes its IPv4 entries up one slot, and spark-4's table has a hole at index 3. Measured

Fabric HCAspark-3 IPv4 RoCE v2 GIDspark-4 IPv4 RoCE v2 GID
rocep1s0f0 (192.168.250.0/24)index 5index 4
roceP2p1s0f0 (192.168.251.0/24)index 5index 4
Fix: mod b12x-roce-gid-auto
  • Behaviour: a negative or unset index now selects, on each node, the lowest index holding an IPv4-mapped RoCE v2 GID on every selected HCA, which is what NCCL does for -1. An explicit non-negative index is still honoured.
  • Why per-node indices are safe: b12x exchanges the GID itself and uses the index only as the local source (_roce_proxy.c lines 178, 281, 305–306). Source
  • Packaging: exact-anchor patch that aborts on drift, idempotent. Added to both the GLM recipe and the DeepSeek 0731 rollback recipe; the 0731 recipe also gained the two enable lines.
  • Tests: on live hardware inside the image, it resolved 5 on spark-3 and 4 on spark-4. Measured

A second blocker: the startup memory check

The first two relaunches with RoCE working failed on spark-4, which reported 103.3 GiB free against the 104.65 GiB that gpu_memory_utilization=0.86 requires. Measured

  • At idle, inside the image, CUDA reports 109.7 GiB free on spark-4 and 111.3 GiB on spark-3. vLLM's startup work therefore uses about 6.45 GiB before the check runs.
  • spark-4's idle state is unchanged since the last good start, so enabling RoCE adds about 1.3 GiB at startup. Only about 0.12 GiB of that is RoCE's buffers; the rest is probably b12x's kernel preparation. Inference
  • Fix: gpu_memory_utilization 0.86 → 0.84. GLM's KV cache is pinned at 6 GiB by kv_cache_memory_bytes, so it loses no capacity.
  • DeepSeek rollback: restore-deepseek0731.sh moved from --gpu-mem 0.85 to 0.84. That trims about 1.2 GiB of its KV cache, because that recipe sizes its cache from this number.

A/B/A on fresh starts

The first comparison against the old container's NCCL numbers showed +27–37%, roughly three times what TensorFold reports for the same change. A fair A/B/A followed, each arm a fresh start with identical settings and only VLLM_ENABLE_ROCE_ALLREDUCE changed.

Reading the table:

  • RoCE's real gain is +7–11% at one stream, consistent across both RoCE arms. At four streams it is +2–6%, inside the run-to-run spread: A1 and A2 differ by up to 8% there. That matches TensorFold's pattern of +10.8% at one stream and +4.3% at four.

Open questions and falsifying tests

  • The weight-bytes share depends on an inference. If the Reederey87 kit actually ran FP8 dense rather than BF16, the weight-bytes share drops to about 10–14% and more of the gap is unexplained. The test is to run TensorFold with BF16 non-experts and drafting off, against the kit with speculative decoding off, with one nsys trace per side. Steps within about 10% of each other mean bytes explain the gap.
  • No per-kernel profile of both stacks in the same run has been published.
  • The fail-stop risk on the fleet lane. A fabric stall now fails a step instead of falling back to NCCL. Watch the lane's error rate after the change.
  • Memory headroom on spark-3. The head node bottoms out at about 1.7–2.1 GiB MemAvailable under this lane, with or without RoCE. That is thin for a unified-memory GB10, where an out-of-memory condition can hang the box. Lowering kv_cache_memory_bytes buys about 285K tokens of context per GiB.
  • The long-running container slowdown. The container that had run for 13 days decoded 17–20% slower than a fresh start of the same configuration. Possible causes include allocator fragmentation, prefix-cache growth and clock behaviour. Test with a scheduled restart and a weekly benchmark.
  • The fold-rollback estimate is arithmetic. Profile one Qwen3.8 MTP-3 decode step at 8 streams and sum the time of the fused_gdn_decode_post_conv_mtp kernels. Well under 3% of the step means it isn't worth the plumbing.
